# 🕹️ 快速上手

以下是一条 14 步的探索路线，带你体验从基本读写、故障注入到动态扩缩容的完整流程。每一步都包含了可执行的操作与预期观察到的现象。

> **前置条件：** 以默认配置，完成 README 中「快速开始」的启动步骤，浏览器打开 `http://localhost:8080`。

## 第一步：了解控制台布局

控制台页面按功能区分为以下几个区域（详细控件说明见 [CONSOLE.md](CONSOLE.md)）：

| 区域       | 位置     | 作用                                         |
|----------|--------|--------------------------------------------|
| **控制操作** | 页面上方   | 包含 KV 读写、CAS 竞赛、批量写入、组操作、网络模拟、观测日志开关等控件    |
| **节点状态** | 页面中部   | 展示所有分片组的节点拓扑，每个节点有指示灯（🟢在线/🔴离线/🟡隔离）和操作按钮 |
| **分片分布** | 节点状态下方 | 展示 12 个分片到各组的映射关系，支持按分片/按组排序切换             |
| **操作日志** | 右侧上方   | 记录你发起的读写、故障注入等操作的结果                        |
| **观测日志** | 右侧下方   | 系统内部事件的实时 SSE 推送，可选择 5 类事件筛选展示             |

默认初始状态：
- **配置仓库**（组 0）：一个独立的 3 节点 Raft 组，存储分片配置
- **组 1**：初始的唯一分片组，3 个节点，当前持有**所有 12 个分片**

> 💡 **提示：** 日志面板和左侧内容区之间的**分隔条可以拖拽**，调整日志区域的宽度；观测日志和操作日志之间的分割比例也可拖拽调整。

> 🎯 **目标：** 了解系统默认的初始状态和各面板的功能。

## 第二步：写入与读取

在左侧 **KV 操作** 区域：

1. 输入 Key = `name`，Value = `distributed-kv`
2. 点击 **Put** → 下方显示 `Put: name = distributed-kv`
3. 输入 Key = `name`，点击 **Get** → 下方显示 `Get: name = "distributed-kv"`

操作日志面板会同步显示操作结果，以绿色标记成功、红色标记失败。

> 💡 **提示：** 输入 Key 时，右侧会实时显示 `→ 分片X` 的提示，告知该 Key 经过哈希计算后属于哪个分片。

> 🎯 **目标：** 验证基本的键值读写功能正常。

> 🤹 **拓展尝试：** 
> - 勾选 **观测日志** → **☑️ KV操作**，对同一个 key 进行两次 Put，观察版本号
> - Get 从未写入的 Key

## 第三步：了解数据分片

在 KV 操作区域的 **随机键值** 下拉框中：

1. 选择目标分片（例如 分片2）
2. 点击 **生成** → 自动填入一个映射到 分片2 的 Key 和随机 Value
3. 点击 **Put** 写入

重复几次，观察不同 Key 落在不同分片。系统页面上已预生成 **Key 池**（每个分片至少 100 个候选 Key），保证你能快速选取目标分片的测试 Key。

> 💡 **提示：** CAS 竞争写入区域也有独立的「随机键值」选择器和「生成」按钮，与 KV 操作共用 Key 池。你将在下一步体验 CAS 的用法。

> 🎯 **目标：** 观察数据按哈希分片存储，了解 Key 池的预生成机制。

## 第四步：CAS 并发竞赛

在 KV 操作区域下方的 **CAS 竞争写入** 区域：

1. 输入 Key = `counter`，或使用 **随机键值** 生成器选取一个 Key
2. 使用默认的并发客户端数（最大不能超过后端客户端池容量）
3. 点击 **开始**

观察结果：5 个客户端同时对 `counter` 发起 CAS Put 操作。由于每个客户端都携带相同的版本号（均为写入前的当前版本），**只有一个操作能成功**，其余返回版本冲突——这就是乐观锁的"先检测后写入"机制。

结果面板会显示：
- ✅ 成功数（通常为 1）
- ⚠️ 版本冲突数（通常为 4）
- 🏆 最终值（最后成功写入的那个值）
- ⏱️ 总耗时

> 🔍 **理解：** CAS（Compare-And-Swap）要求客户端先通过 Get 获取键的当前版本号，然后在 Put 时携带此版本号。服务端只有在当前版本与请求版本一致时才会更新。这保证了"写入基于最新的已观测状态"，是分布式系统中实现乐观并发控制的常用手段。

> 💡 **提示：** 
> - 系统支持的最大并发客户端数由后端的客户端池容量决定（可在 `config.yaml` 中配置 `clerkPoolSize`）。前端会自动同步此上限到输入框的 `max` 属性。
> - 勾选 **控制操作** → **观测日志**  面板中 **☑️ KV操作** 可从客户端的角度来观察读写实际操作。

> 🎯 **目标：** 观察基于版本号的 CAS 如何保证并发写入的线性一致性。

## 第五步：批量随机写入

用于测试系统在高并发写入下的吞吐量。

在 **CAS 竞争写入** 区域下方的 **批量随机写入** 区域：

1. 设置写入数量为 `200`（范围 1~10000）
2. 目标分片选择「任意」（或指定特定分片）
3. 点击 **开始**

观察结果：系统会从后端客户端池中借用多个客户端并发执行 CAS Put 操作，完成后显示成功/失败数量和总耗时。

> 🔍 **理解：** 后端使用客户端池（默认 500 个），批量写入时会从池中借用客户端并发执行，最大并发度受池容量限制。每个键的写入采用 CAS 语义（先 Get 版本号再 Put），因此并发下部分请求可能因版本冲突失败。这一步与上一步的区别在于：CAS 竞赛是**多客户端竞争同一 Key**，批量写入是**多客户端并发写入不同 Key**。

> 🎯 **目标：** 体验并发批量写入的性能表现，了解后端客户端池的并发机制。

## 第六步：节点宕机——多数在线，服务不中断

这是 Raft 容错的第一层验证：只要组内多数节点在线，服务就不受影响。

在**节点状态**面板中：

1. 找到 `组 1` → 节点 `server-1-0`
2. 点击 **终止** → 该节点指示灯变为 🔴

回到 KV 读写区域，尝试 Get 刚才写入的 Key——**操作仍然成功**。

> 🔍 **理解：** Raft 要求多数节点（3 节点中至少 2 个）同意才能提交。宕机 1 个还剩 2 个，仍满足多数条件，所以读写完全不受影响。

> 🎯 **目标：** 验证 Raft 的"多数容错"——少数节点（1/3）宕机不影响读写。

## 第七步：继续宕机——多数离线，服务中断

现在我们来触碰 Raft 的**容错边界**：

1. 选择 `组 1` → 节点 `server-1-1`
2. 点击 **终止** → 该节点指示灯变为 🔴

此时组 1 的 3 个节点中**已有 2 个宕机（2/3）**，只剩下 1 个节点在线。

尝试 Get/Put 刚才写入的 Key——**操作失败**（无响应）。

> 🔍 **理解：** 3 个节点中只有 1 个在线，不满足"多数（≥ 2）"条件，Raft 无法选举出领导者，也无法提交任何日志。这是分布式系统"可用性"与"一致性"之间的权衡——为了保证数据不分裂、不丢失，宁愿暂停服务也不提供错误数据。

> 🎯 **目标：** 验证 Raft 的"容错边界"——多数（≥ 2/3）节点宕机后服务不可用。

## 第八步：恢复节点——服务自动恢复

现在把宕机的节点重新启动。

1. 选择 `组 1` → 节点 `server-1-0`，点击 **启动** → 恢复 🟢
2. 选择 `组 1` → 节点 `server-1-1`，点击 **启动** → 恢复 🟢

此时组 1 的 3 个节点**重新全部在线**。等待，直到观察到 Raft 选出领导者。

尝试 Get 刚才写入的 Key——**操作成功**，数据完好无损。

> 🔍 **理解：** 即使所有节点都宕机过，只要重新启动，它们就会从持久化存储中加载之前的日志，重新建立 Raft 集群，自动同步数据，继续对外提供服务——整个过程对上层用户透明。

> 🎯 **目标：** 观察 Raft 的宕机后恢复能力——节点重启后自动重建集群、同步数据。

## 第九步：节点隔离 vs 终止——两种故障模式

系统提供了两种不同的节点故障模拟方式，它们的行为有本质区别：

| 操作     | 节点状态点 | 故障类型  | 行为                               |
|--------|-------|-------|----------------------------------|
| **终止** | 🔴 红点 | 进程级故障 | 杀死进程，节点完全消失，无法响应任何请求             |
| **隔离** | 🟡 黄点 | 网络级故障 | 进程仍在运行，但与其他 Raft 节点的网络被切断，模拟网络分区 |

### 体验隔离领导者

在组 1 全部节点在线时：

1. 观察哪个节点是 **领导者**（发光绿点 + "Leader 在线" 标签）
2. 点击该节点的 **隔离** 按钮 → 该节点变为 🟡（发光黄点 + "Leader 隔离" 标签）
3. 观察几秒，系统自动触发重新选举：
   - 原来的 领导者 被隔离后，跟随者 因收不到心跳触发选举
   - 一个新的节点成为 领导者（变为发光绿点）
4. 操作隔离期间的数据读写——短暂中断后自动恢复

### 体验网络恢复

1. 点击被隔离节点的 **恢复** 按钮 → 节点重新变为普通 🟢（跟随者 状态）
2. 该节点重新加入集群，通过日志同步追赶隔离期间遗漏的数据/快照

> 🔍 理解 **终止** 和 **隔离** 的核心区别：
> - **终止** 是节点完全消失，重启后需要加载持久化状态从头参与集群
> - **隔离** 是节点进程仍在运行，只是网络断开。恢复后节点可能仍有旧领导者的状态，发现任期落后后自动降级为 跟随者

> 🎯 **目标：** 区分进程级故障（终止）与网络分区（隔离）两种故障模式，观察系统对二者不同的容错行为。

> 🤹 **拓展尝试：** 
> - 终止一个节点，隔离另一个节点，尝试 PUT / GET，系统是否能提供服务？
> - 隔离一个领导者节点，几秒后恢复，领导权是否会变更？隔离一个 跟随者 节点，几秒后恢复，领导权是否会变更？ (工业级 Raft 会使用 `PreVote 机制`优化，本实现无此机制)

## 第十步：动态扩缩容与分片迁移

### 扩容——添加新组

在**组操作** / **节点状态**面板中，点击 **+ 新组加入** 按钮：

- 出现 组 2，包含 3 个新节点（全部 🟢）
- **分片分布面板**中，部分分片的颜色从组 1 变为组 2——数据正在自动迁移到新组
- 等待期间，标题栏会显示黄色 **⚠ 分片迁移未完成** 徽章，迁移完成后自动消失
- 几秒后，12 个分片重新均匀分布到 2 个组（每组 6 个分片）

**验证：** 回到 KV 操作区域，Get 第二步写入的 `name`——分片 2 已经移动到新的组中，数据仍在，说明分片迁移过程中数据完好无损。

> 💡 **提示：** 点击分组卡片上的 **日志** 按钮，可以打开/关闭该组的观测日志，以筛选自己想关注的组，消除不必要的噪音。

### 缩容——让组离开

在**组操作**中选中 组 2（在「组操作」下拉框中选择），点击 **移除**（或直接在 **节点状态** 中点击对应组卡片中的 **移除** 按钮）：

- **分片分布面板**中，分片从 组 2 逐个移回 组 1
- 组 2 的所有节点从拓扑中消失
- 等待 **⚠ 分片迁移未完成** 徽章消失，12 个分片全部回到组 1 中

**验证：** 再次 Get `name`——数据依然可读，确认缩容迁移不会丢失数据。

> 💡 **提示：** ConfigStore（组 0）是系统配置仓库，系统会阻止你移除它。如果尝试在「组操作」中移除它，会收到明确的拒绝提示。

> 🎯 **目标：** 演示水平扩展和缩容场景，观察「⚠ 分片迁移未完成」徽章和分片分布面板的实时变化。

> 🤹 **拓展尝试：** 在**分片迁移**未完成时，(多次)尝试 **加入新组**，或者 （多次）**移除** 现存的组，观察系统的容错边界（可能需要打开 **不可靠网络** 延缓系统才能在分片迁移完成前完成操作）。

## 第十一步：开启观测日志看系统内部

系统内置了 5 类观测日志，通过 SSE 实时推送，让你看到系统内部的运行细节。

### 开启观测日志

在 **观测日志** 区域，点击你想观察的事件类别标签：

| 标签         | 关注的事件                  |
|------------|------------------------|
| **Raft选举** | 领导者选举、任期变更、投票过程、节点身份变更 |
| **Raft复制** | Raft 领导者发送日志追加和安装快照    |
| **Raft快照** | 状态机压缩为快照、节点重启后从快照中恢复   |
| **KV操作**   | 键值读写提交、去重、版本变化，及重试机制   |
| **分片迁移**   | 冻结/安装/删除 三阶段进程         |

点击任一类别的开关后，观测日志面板自动展开，开始实时推送事件。

### 迁移子类型颜色编码

当迁移事件发生时，日志会以不同颜色区分操作阶段：
- **冻结 (Freeze)**：🔵 冰蓝色，表示旧组停止接受写入
- **安装 (Install)**：🟢 绿色，表示新组安装分片数据
- **删除 (Delete)**：🟠 琥珀色，表示旧组清理旧副本

### 组合体验

在观测日志开启的状态下，执行**上一步的扩缩容操作**，观察完整的迁移流程日志。

> 💡 **提示：**
> - 可以同时选择多类事件标签，日志会混合展示
> - 每个组卡片上都有独立的 **日志** 按钮，点击后可以过滤只显示该组的事件
> - 配置仓库的日志默认关闭，需要手动点击其日志按钮开启
> - 观测日志面板支持**清空**和**拖拽调整大小**，与操作日志共用右侧面板

> 🎯 **目标：** 理解系统内部的事件流，使用观测日志观察系统内部行为。

## 第十二步：不可靠网络下的系统行为

在**控制操作** → **组操作**区域下方的**不可靠网络**面板中，打开开关：

系统提供了4个独立的网络模拟参数：

| 控制项          | 默认值      | 说明                                                |
|--------------|----------|---------------------------------------------------|
| **丢包率**      | 10%      | RPC 请求或回复被随机丢弃的概率，滑块可在 0%~100% 间调节                |
| **RPC 请求延迟** | 0~27ms   | 每个 RPC 请求附加的随机延迟（模拟网络拥堵）                          |
| **RPC 回复乱序** | 关闭       | 开启后，2/3 的 RPC 回复会被延迟 200~2200ms，模拟 TCP 重传导致的旧消息晚到 |
| **断连延迟**     | 0~7000ms | 当节点断连时（隔离/终止），其他节点对RPC回复的最大等待时间                   |

> 💡 **提示：** 以上参数在不可靠网络关闭时自动处于禁用状态，开启后才可调节。

操作步骤：
1. 打开**不可靠网络**开关
2. 尝试 Get/Put 刚才写入的 Key——可能偶尔变慢或需要重试，但最终结果一致
3. 调高丢包率（如 50%），观察请求耗时和重试次数的变化；观察 Raft 节点领导权是否能保持稳定
4. 开启**RPC 回复乱序**，模拟更极端的网络条件

> 🔍 **理解：** 丢包 + 延迟 + 乱序是真实网络环境中最常见的三类故障。本系统通过重试和超时机制屏蔽了这些底层波动，对外仍保持线性一致的读写语义。

> 🎯 **目标：** 了解系统提供的网络故障模拟，体验网络故障下系统的容错率。

## 第十三步：混沌猴子——自动故障注入

在拓扑面板中，点击 组 1 标题旁的 **混沌** 按钮：

- 按钮变为红色「混沌中」状态
- 系统每 1～3 秒随机杀死一个节点，同时**确保大多数节点在线**
- 拓扑中节点指示灯随机变化 🟢↔🔴
- 在此过程中反复执行 Get/Put——系统持续可用

再次点击 **混沌** 按钮可关闭自动故障注入。

> 💡 **提示：** 你也可以在混沌猴子运行时，配合**观测日志**中的 Raft 选举标签一起观察，可以看到频繁的领导权变更记录。

> 🎯 **目标：** 通过长时间压力测试展示系统在持续故障下的健壮性。

##  🎮 自由探索

以上是预设的路线，你还可以自由组合各种 **破坏性操作 😈** 来测试系统的容错边界。以下是一些可能的操作组合：

- **全组宕机再恢复：** 终止组 1 全部 3 个节点 → 等几秒 → 全部启动，观察 Raft 如何从头重建集群
- **迁移中途终止组：** 添加新组后（分片正在迁移时）立刻终止其中一个组，观察迁移能否完成；恢复组后观察是否能自动完成
- **不可靠网络 + 持续读写：** 开启不可靠网络后持续 Put/Get，观察系统能否最终保持一致
- **混沌猴子 + CAS 并发：** 启动混沌猴子后运行 CAS 并发竞赛，验证线性一致性在持续故障下是否依然成立
- **批量写入压测 + 混沌猴子：** 同时启动混沌猴子和批量写入，观察系统在持续故障下的吞吐稳定性
- **迁移中分片读写：** 打开不可靠网络，分片迁移进行中时，分别对不受影响和受影响的分片调用批量写入，观察是否可以成功  (小技巧：可以临时终止分片迁移涉及的组，让分片迁移无法完成，以便观察)
- **终止配置仓库节点：** 对配置仓库中的节点执行终止，观察是否影响分片读写和分片迁移

> ⚠️ 注意： 如果系统不幸崩溃，将无法在中断时清理子进程，请使用 `make clean` 来清理泄漏的 daemon 进程
